# Decision Registry

> Bridge between scientific findings (Stage 3.3/3.4/3.5) and future engineering work (Stage 4).
> Updated after every analysis completes. Each entry links a decision to the evidence that supports it.

## Schema

Each entry:
- **Decision** — the architectural or model choice being considered
- **Evidence** — what data supports or refutes it
- **Supporting hypotheses** — which hypothesis registry IDs (e.g., 3.4-A, 3.5-P)
- **Supporting benchmark(s)** — which benchmark artifacts (file paths)
- **Confidence** — High / Medium / Low
- **Status** — Accepted / Deferred / Rejected / Pending

### 2. Qwen2.5-0.5B as default generator

- **Decision:** qwen2.5-0.5b is the default generator (latency binding constraint for EEG communication)
- **Evidence:** Stage 3.3 two-model comparison: 40.9 tok/s vs gemma-3n-e2b 7.2 tok/s (p<0.0001, d=17.7); Pareto-optimal on latency. Frozen fleet leaderboard (2026-07-14, 16 evaluated): qwen2.5-0.5b rank #2 (score 0.801), behind tinyllama-1.1b (#1, 0.843) and ahead of smollm2-360m (#3, 0.784) — all three Pareto-optimal. qwen2.5-0.5b has the lowest RSS of the top 3 (707 MB vs tinyllama's 1455 MB). Reproducibility caveat (repro_report, 2026-07-14): generation quality metrics vary run-to-run beyond tolerance (instruction_following ±0.2, stability ±0.06 observed on the qwen repro pair), so the top-3 composite ordering is within measurement noise on its quality components.
- **Supporting hypotheses:** 3.4-E **evaluated** — 10 generators, 45 pairs, 27 prompts, mean pairwise cosine ~0.55 (generators genuinely divergent), see `generator_comparison.json`
- **Supporting benchmark(s):** `Evaluation/results/leaderboard.json`, `Evaluation/results/stage_3_4/generator_comparison.json`, `Evaluation/results/repro/repro_report.json`
- **Confidence:** Medium — fleet evidence complete, but the #1/#2 composite gap is inside observed run-to-run variance
- **Status:** Accepted. Human review completed 2026-07-16 (Stage 3.5 readiness signoff): qwen2.5-0.5b confirmed as default over tinyllama-1.1b. Reasoning — tinyllama's composite advantage (0.843 vs 0.801) is within the run-to-run variance noise documented above, so it isn't a reliable quality edge; qwen's ~2× lower RSS (707 MB vs 1455 MB) matters more here than in a typical eval, since the generator process shares memory with live EEG windowing, classification, and spectral encoding. This resolves `Evaluation/reports/STAGE_3_5_READINESS.md`'s signoff condition #2 and unblocks Stage 3.5 policy-registry work (`3.5-P`, `3.5-D`) from encoding this default.

### 8. Stage-5 hypnagogic loop — deliberate, scoped network-egress exception

- **Decision:** The opt-in, experimental Stage-5 hypnagogic dialogue loop (`HypnagogicDialogueLoop`) may use a **cloud LLM** for its short "mirror" replies, via the `claude` CLI (`ClaudeCLIGenerator`, Sonnet 5 on the user's subscription, no API key). This is the **first deliberate exception** to the "No network at runtime" invariant (CLAUDE.md line 3 / PRINCIPLES.md Principle 5), made by explicit informed user decision (2026-07-19) after the on-device LLM path was empirically falsified for the harder drift task this session. (A second, independent exception — the two-machine peer bridge — is entry 9, added 2026-10-11; it does not change anything below about this one.)
- **Evidence / rationale:** (a) On-device small models were falsified for semantic drift ranking (entry 7); the user accepted cloud rather than ship a weak local model. (b) The egress is **tightly scoped**: quarantined in a dedicated `BCICloudBridge` target (never `BCILLM`, which the boundary contract keeps on-device), used only by this one opt-in loop. (c) **Audio never leaves the machine** — STT is on-device (`HypnagogicListener`, `requiresOnDeviceRecognition`); only the resulting *transcript text* is sent to the CLI. (d) **Nothing is persisted** — transcripts and replies are ephemeral, in-memory, dropped per turn. (e) Off by default behind `hypnagogicLoopEnabled`, with a persistent `PrivacyIndicatorView` badge and an honest `Info.plist` mic-usage string while active. (f) The generator's default system prompt is constrained (passive mirror, no questions, ≤2 soft sentences).
- **Scope guard — what this does NOT do:** it does **not** relax the invariant anywhere else; every other `Sources/` path remains zero-egress by construction. It is **manually triggered only** — NOT wired to the S-3 N1 detector (synthetic-only, unvalidated, N1 sensitivity ≥0.40; entry 7 / SLEEP_CYCLE_DESIGN.md §16). It is **engineering scaffolding, not a validated intervention** — any efficacy/"steering" claim still requires the D8 OSF pre-registration ("non-negotiable"). The Stage-4 gates (AA6545F1 FSM, EF7BC788 audio-cue engine, B4BBC32A on-device dream-analysis LLM) remain unbuilt and gated; this loop is not a substitute for them.
- **Supporting benchmark(s):** `Sources/BCICore/Composition/HypnagogicDialogueLoop.swift`, `Sources/BCICloudBridge/ClaudeCLIGenerator.swift`, `Sources/BCIVoice/HypnagogicListener.swift`, `Sources/BCICore/Protocols/{HypnagogicListening,SpeechSynthesizing}.swift`, `Data/s2_claude_sonnet5.json` (the Sonnet-5 offline benchmark that motivated the transport choice).
- **Confidence:** Medium — the engineering is isolated, opt-in, and honestly bounded; the *intervention's efficacy* is unproven and explicitly out of scope. The `claude` CLI runtime dependency (binary on PATH + signed in; would break under App Sandbox — none today) is a known fragility.
- **Status:** Accepted for the experimental, opt-in loop only. At the time of this entry, network egress was possible in the runtime exclusively through `BCICloudBridge` behind `hypnagogicLoopEnabled`; entry 9 adds a second, independently-gated path (`BCIPeerBridge`) — see that entry for its own scope guard.
- **Amendment (2026-10-13):** point (d) no longer holds for the dialectic modes. Each voice's prompt now carries up to the last 4 exchanges of the conversation (what was heard and what was voiced), held in memory by `ConversationHistory` and re-sent with every call, so earlier transcript text leaves the machine again on later turns. This path still writes nothing to disk (the Interaction Log is separate and opt-in), and the history is cleared when the loop is turned off or the runtime changes. Mirror mode and the Witness prompt are unchanged. Reason: the 2026-10-13 interaction log showed follow-ups answered without their context ("reiterate on that framework" → "don't reiterate the framework at all").

### 9. Two-machine hypnagogic dialectic bridge — second deliberate network-egress exception

- **Decision:** The opt-in `HypnagogicDialecticLoop` may, behind a new `NEURALCOMPOSE_BRIDGE_PEER` / `NEURALCOMPOSE_BRIDGE_SESSION` launch-environment pair, swap its injected `listener`/`speaker` seam (`any HypnagogicListening` / `any SpeechSynthesizing`) for a direct TCP connection (`BCIPeerBridge`) to a peer machine over Tailscale, carrying this side's heard/spoken turn text as newline-delimited JSON lines. This is the **second deliberate exception** to the "No network at runtime" invariant (CLAUDE.md line 3 / PRINCIPLES.md Principle 5; the first is entry 8), made by explicit informed user decision (2026-10-11), to run a two-machine dialectic experiment: this Mac against a Linux GPD device's Rust client (`feat/hypnagogic-linux`), comparing the GPD side's drift-anchor + repetition-floor guard on vs. off, with this Mac as a fixed, unguarded interlocutor in both arms.
- **Evidence / rationale:** (a) The seam already existed as dependency-injected protocols; no change to `HypnagogicDialecticLoop`'s control flow, timing, or telemetry was required — confirmed by independent recon on both sides (Mac and GPD) before either wrote code, with the design (wire format, the GPD's `--peer`/`--bridge` flag, this side's env-var trigger) agreed across both sessions first. (b) Egress is quarantined in a new, dedicated `BCIPeerBridge` target, mirroring `BCICloudBridge`'s quarantine: depends only on `BCICore`, imported only by `NeuralComposeApp`. (c) Off by default — both env vars must be set; absent them, `ensureHypnagogicLoopRunning()` builds the original mic/`AVSpeechSynthesizer` pair unchanged. (d) Unlike entry 8, this is not text-to-a-cloud-API — it is this device's own turn text to a second device the same user controls, reachable only over Tailscale (the same threat model `MindMonitorOSCStream`'s OSC listener already documents: reachable only to tailnet peers, never the public internet). (e) Turn text already reaches disk when `interactionLoggingEnabled` (ADR-005, pre-existing, opt-in, never transmitted); the bridge does not change that — it adds a second machine as recipient of this side's turns over the wire, in addition to this side's own local log.
- **Scope guard — what this does NOT do:** it does **not** relax the invariant for `HypnagogicDialogueLoop` (mirror mode) or any other loop — the bridge wires in only where `ensureHypnagogicLoopRunning()` already injects a listener/speaker. It does **not** touch `BCILLM`'s on-device boundary — no generation crosses the wire, only already-generated/heard text. It sends **no audio** — Stage 1 (this entry) is text-only; a Stage 2 adding real TTS/ASR per side is explicitly out of scope here and would need its own evidence/decision. It does **not** check the peer's tailnet identity against an allow-list — the GPD-side listener accepts any connecting peer; acceptable for a two-person, two-machine tailnet with no other expected traffic on port 7373, not a pattern to carry over if this bridge is ever exposed more broadly.
- **Supporting benchmark(s):** `Sources/BCIPeerBridge/{PeerWireLine,PeerBridgeConnection,TCPPeerSeams}.swift`, `Sources/NeuralComposeApp/PeerBridgeConfiguration.swift`, `Sources/NeuralComposeApp/AppViewModel.swift` (`connectPeerBridge`), `Tests/BCIPeerBridgeTests/PeerBridgeConnectionTests.swift` (loopback round-trip), and the GPD-side `--bridge <session>` flag in `crates/neuralcompose-hypnagogic/src/main.rs` at commit `853f6ce` on `feat/hypnagogic-linux` (uncommitted on that worktree at the time of this entry).
- **Confidence:** Medium — the engineering mirrors an already-reviewed quarantine pattern (entry 8) and the wire format was fixed and agreed by both sessions before either wrote code; the *experiment's* statistical power is explicitly low (3 runs/arm, pre-registered as showing a large effect or nothing reliable) and is out of scope for this entry, which covers the bridge mechanism only.
- **Status:** Accepted for the experimental, opt-in bridge only. Network egress is now possible in the runtime through exactly two quarantined, independently-gated paths — `BCICloudBridge` (entry 8) and `BCIPeerBridge` (this entry) — both opt-in and off by default; the invariant otherwise stands.

### 10. Biofeedback egress (ADR-011) : scoped network-egress exception, derived features only

- **Decision:** A new `BCIBiofeedback` target may emit EEG-derived features (per-channel band powers in Bels, per-channel health, Track A blink/clench events, IMU) over two transports: a CoreMIDI virtual source (in-machine, not network) and OSC/UDP to a user-chosen host, loopback `127.0.0.1:7000` by default. This is a deliberate exception to the "No network at runtime" invariant (CLAUDE.md line 3 / PRINCIPLES.md Principle 5) alongside entries 8 (`BCICloudBridge`) and 9 (`BCIPeerBridge`), and the only one that carries EEG-derived numbers. Accepted 2026-11-07; status follows ADR-011.
- **Evidence / rationale:** (a) The inbound half of the Muse-to-DAW chain already exists (`MindMonitorOSCStream`, ADR-004); the outbound half is what makes NeuralCompose usable as an open biofeedback instrument alongside Mind Monitor + Muse Port. (b) The egress is **tightly scoped**: one target, dependencies `BCICore` + `BCIEEG` only, imported only by `NeuralComposeApp`, never a dependency of another `BCI*` target. (c) **Raw EEG never reaches a frame**: the egress boundary is `BiofeedbackFrame`, a function of band powers, health, events and IMU; raw `/muse/eeg` re-broadcast is a separate explicit toggle through the one named helper `MindMonitorMirror.rawEEG(_:)`. (d) **Health gating is mandatory**: every `BiofeedbackMapping` carries a `HealthPolicy` (default `holdLast`); Mind Monitor's behaviour is available only as the explicit `passthrough` policy. (e) **Deterministic**: pure-Swift periodogram and a clock-free mapper, so a recording through a mapping set yields byte-identical outputs for the replay regression. (f) Off by default; while off the app wires `NullBiofeedbackSink`. (g) No third-party dependency; Network and CoreMIDI are system frameworks behind `canImport`.
- **Scope guard - what this does NOT do:** it does **not** touch `BCICloudBridge` or `BCIPeerBridge` or widen entries 8 and 9; cloud egress stays exclusively in `BCICloudBridge`. It adds no HTTP client. It does not enable macOS Network MIDI (an OS feature the user controls in Audio MIDI Setup). It does not expose World Model or Laya latents as features; that waits for a benchmarked encoder and its own amendment. The `MindMonitorMirror` compatibility output is ungated by design and says so; gating is the mapper's job.
- **Supporting benchmark(s):** `Tests/BCIBiofeedbackTests/BandPowerEstimatorTests.swift` (A^2/2 physical-unit checks, FFT vs naive DFT), `FeatureMapperTests.swift` (all four health policies, smoothing, rate limit, MIDI quantisation, note gates, determinism), `MindMonitorMirrorTests.swift` (address scheme, payload shapes, bundle round trip through `MuseOSCDecoder`), `Tests/BCIEEGTests/OSCEncoderTests.swift`. Golden-recording replay fixture is a follow-up issue and gates live validation.
